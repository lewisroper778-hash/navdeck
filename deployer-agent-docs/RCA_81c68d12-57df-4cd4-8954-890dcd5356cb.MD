## Root cause (mechanism — consistent with all evidence; NOT reproduced in sandbox)
Clean clients work, the user's own devices don't, and nothing reaches the backend. This is a stale service-worker / cache stranding after the redeploy:
- The app registers a service worker on load: `src/index.js:26 navigator.serviceWorker.register("/sw.js")`. Live `/sw.js` = network-first, constant cache key `CACHE = "navdeck-v2"` (does not change per deploy).
- `sw.js` fetch handler caches every same-origin non-/api GET (incl. the app shell `/` and hashed `/static/js/*.js`), and on network failure for a navigation falls back to the cached `/`.
- A device still controlled by a PRIOR cached state serves an old cached index.html that references old hashed chunk(s) (e.g. an older `main.<hash>.js`). After the redeploy those old chunk files no longer exist on the server, so the script fails to load → the React app never boots → **blank page**. Because that stale/old bundle predates (or never reaches) the new reporter, nothing is POSTed to `/api/client-errors` → empty collection + no backend logs.
- A fresh headless Chromium has no SW/cache → loads the current build fine. navdeck.online / www → 301 to emergent.host is healthy and unrelated.
- iOS standalone (home-screen) PWAs are especially prone to this because they don't reliably update the controlling SW; that matches the iPad home-screen app + iPad Safari + desktop (previously-visited) all being blank while a clean browser is fine.

Not reproducible from the eph sandbox: it has no browser-side SW/cache and no client state. Server side + the shipped bundle + the SW source were inspected directly; the mechanism follows from `sw.js` + `index.js` + the hashed-chunk build.

## What is NOT the cause (ruled out)
- Not a secrets problem — `/api/clerk/config` returns the correct live key + proxy_url.
- Not a bad/old production build — prod serves the current `main.4aada7ee.js` with the prod URL baked and the reporter present.
- Not the backend — reporter endpoint `POST /api/client-errors` (server.py:796-799) and TTL/index are intact; backend serves `/` and `/api/clerk/config` with 200.
- Not a domain/SSL problem — default host serves; navdeck.online/www 301 correctly.
- Not tier/OOM/platform — active run is healthy (success).

## Suggested fixes
### User (one-time, confirms the diagnosis)
Clear the stale SW/cache on each affected device:
- Desktop browser: hard reload / "Empty cache and hard reload", or clear site data for navlog-pilot.emergent.host (and navdeck.online).
- iPad Safari: Settings → Safari → Advanced → Website Data → remove NAVDECK/navdeck entries.
- iPad home-screen app: delete the installed app and re-add it from the site.
- If any screen renders, the in-app "Clear saved data" button (ErrorBoundary.reset) already unregisters the SW and clears caches.
After this the device should load the current build. If a device still goes blank afterwards, capture the DevTools Console/Network (the failing request / error) and re-report.

### Code (E1) — harden against redeploy stranding (prevents recurrence)
- Version the SW cache per build: make `CACHE` build/hash-stamped (not a constant `"navdeck-v2"`) so each deploy invalidates old entries; keep the activate-time purge of non-current caches.
- Add a ChunkLoadError self-heal: on a failed lazy `import()` / script `error`, run the ErrorBoundary.reset flow (unregister SW + clear caches + one-time `location.reload`) so stranded clients auto-recover instead of showing a blank page.
- Reconsider the navigation fallback: don't serve a cached stale app shell whose referenced chunks may be gone — revalidate the shell (or bust on new build).
Note: this is also why the reporter captured nothing — stranded clients never run the new reporter; the self-heal is what makes recovery (and future reporting) reliable.
