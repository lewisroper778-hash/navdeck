# RCA — navdeck.online login page blank

## Problem statement
Live login page renders blank on all clients (desktop browser, iPad Safari, iPad home-screen PWA) when reached via the custom domain **navdeck.online / www.navdeck.online**. Reporter also observed TLS handshake failures on HTTPS, Cloudflare error 1001 on HTTP, stray 302 redirects to the Emergent host, and `clerk.navdeck.online` pointing at the Emergent host instead of Clerk's Frontend API.

## What I verified (evidence)
- **App is healthy on its own URL.** `preview_health_check` on `https://navlog-pilot.emergent.host/` → **200**, 581 ms, real NAVDECK HTML served (title "NAVDECK · Flight Sim EFB"). The application/frontend/backend are fine.
- **Custom domains are NOT verified and DNS is misconfigured.** `list_domains`: both `navdeck.online` and `www.navdeck.online` → `verified: false`, provider `cloudflare`. `check_domain_status`: both → `linked: false`, message **"A records do not point to expected IPs"**.
- **Clerk secrets present.** `list_secrets` (active run dc770d1b): `CLERK_PUBLISHABLE_KEY` and `CLERK_SECRET_KEY` both non-empty. Deployment is a `cloudflare` frontend type.

## Root cause
The blank page is **not an application bug** — it is a **custom-domain DNS/SSL configuration problem on the user's side**:

1. **DNS for navdeck.online / www.navdeck.online does not point at the Emergent custom-hostname target.** Because the domain is unverified, Cloudflare has **not issued an edge SSL certificate** for it → the `sslv3 alert handshake failure` on HTTPS. Over HTTP the records are inconsistent — sometimes unresolved (Cloudflare **error 1001 = DNS resolution error**), sometimes caught by a stray 302 redirect to `navlog-pilot.emergent.host`. Net effect: the browser never successfully loads the app bundle over the custom domain, so the login page is blank.

2. **Clerk production domain is not set up.** `clerk.navdeck.online` is the Frontend API host encoded in the `pk_live` key, but it currently 302-redirects to `navlog-pilot.emergent.host` instead of being a CNAME to Clerk's Frontend API. The required Clerk production DNS CNAMEs (clerk, accounts, clkmail, clk._domainkey, clk2._domainkey) have not been created. Note: the app sets `proxy_url=/api/__clerk`, so FAPI is reachable via the backend proxy once the domain itself loads — but the Clerk DNS records should still be created to make the pk_live host resolve correctly and avoid the stray redirect.

## What the user must change
Everything is in the user's DNS / Cloudflare account and the Clerk dashboard. Nothing can be fixed from the deployment pipeline (no redeploy helps).

### A. Fix the Emergent custom-domain DNS + SSL
- Open **Deployment Panel → Domains** and copy the exact DNS record target shown there for `navdeck.online` and `www.navdeck.online`.
- At the DNS provider (Cloudflare) set the records **exactly** as shown — remove the current A records that point elsewhere.
- Remove the stray **302 redirect rule / Page Rule / Bulk Redirect** in Cloudflare that sends `navdeck.online` → `navlog-pilot.emergent.host`; it is intercepting the apex and masking the real target.
- Wait for the panel to show **verified** and SSL issued. Confirm with the live DNS check. Until verified, HTTPS will keep failing the TLS handshake.

### B. Set up Clerk production DNS
- In the **Clerk dashboard** for the production instance (which uses `clerk.navdeck.online`), copy the DNS CNAME records Clerk lists (clerk, accounts, clkmail, clk._domainkey, clk2._domainkey).
- Create those CNAMEs at the DNS provider pointing at Clerk's targets. Remove any redirect currently making `clerk.navdeck.online` 302 to the Emergent host.

## Not the cause
- App code, frontend build, backend, and MongoDB — healthy (default URL serves 200). 
- Secrets — Clerk keys present and non-empty. No secret change required.
